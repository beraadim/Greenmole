## Changes

### Bounded indexed-PNG preparation

Prepare the RGB24 palette and index rows together where the complete row table
and byte indices fit within **64 KiB combined**. Initially hold at most
**4 KiB of indices on the stack** while checking palette eligibility. An
eligible prefix is copied into the existing contiguous row block, and
remaining indices are emitted during palette construction. This removes the
second source walk and repeated palette lookup for eligible small images.
The allocation decisions occur at chunk/row boundaries.

The 64 KiB limit applies to speculative row-table/index storage; the separate
4 KiB prefix, existing palette, libpng state and codec buffers are not included.
It is not a cap on all PNG memory. Larger images finish palette preflight before
allocating their full row block, then generate indices in a second pass. Counting
row-table bytes prevents a tall narrow image from bypassing the speculation bound.
No new storage is retained by a worker or display between calls.

The color map mixes all RGB bits and computes an odd secondary probe step only
after a collision. Insert and find share the same lookup. The odd step visits
all 4,096 buckets, and at most 256 occupied entries bounds lookup to 257 probes.
This avoids the old hash's clustering of 256 grayscale colors into only sixteen
initial buckets. Consecutive identical colors reuse the preceding index.

Palette order still follows each RGB color's first row-major occurrence.
Bit-depth thresholds, packing, compression/filter defaults, image geometry and
encoded payload bytes are preserved. RGB24's unused high byte remains ignored;
source pixels and padding are unchanged. Positive/negative strides,
bottom-reaching nonzero-origin views and prefix seams inside a row are covered.
ARGB32 and images exceeding 256 colors retain the Cairo writer. There is no
palette quantization, quality reduction or codec-policy change.

A failed optional staging allocation completes palette preflight without
indices. High-color images can still use Cairo; eligible palettes retry normal
final allocation. If that also fails, the writer returns an error without
partial output or leaked owners. Palette OOM retains the Cairo fallback.
Palette/row pointers are acquired before `setjmp()` and remain unchanged during
libpng calls, preserving cleanup after early and post-blob output `longjmp()`.

Easy palettes can gain little or incur extra preparation overhead. A 257th
color discovered after the prefix can require bounded speculative staging
which the old path avoided. These tradeoffs must remain visible in the final
matched measurements rather than being inferred from reduced probe counts.

### Browser multi-image frame readiness

Retain a readiness cursor identifying the first unresolved task in each fixed
frame task array. Image completions previously retried from its beginning,
repeatedly scanning already-ready tasks; sequential completions could perform
quadratic predicate work. Tasks only unblock, so the cursor can advance without
skipping pending image work. Cancellation discards both the task array and its
cursor, including callbacks reaching a reused display.

Each frame still waits for every image before drawing or acknowledging its
tasks. Drawing remains atomic per frame, task order is unchanged, and a later
ready frame cannot overtake an earlier blocked frame. The existing
eight-millisecond/sixteen-frame catch-up limits, immediate isolated-frame
rendering, native decoder ownership, MessageChannel continuation and
acknowledgement callbacks remain unchanged. No new production counter, clock,
setting or per-image allocation is introduced.

The separate readiness benchmark distinguishes counted predicate work from
unmodified-source elapsed timing. Count-only pages exercise sequential,
shuffled and reverse completions. Timing pages stream real PNG/WebP into
browser decoders and canvases using 40/128-image frames, four warm-ups and
24 measured frames per replay, with a target minimum 16 ms source interval.
Pixels, image counts and ordered acknowledgement callbacks are checked.
Predicate reduction alone does not establish a live-client speedup; native
decode/canvas costs can dominate. Physical paint/FPS, wire ACK delivery,
capture, RDP, Wi-Fi, physical input and background-tab behavior are excluded.

### Fail socket writes cleanly

Preserve positive partial writes while rejecting zero progress and impossible
handler counts for nonempty input. Keep handler results as `ssize_t`, propagate
both positive and negative generic failure conventions into Base64/instruction
output, and stop without writing a trailing instruction terminator after a
failure. An attempted Base64 prefix is not replayed because some bytes may
already have reached the peer.

The fd driver retries interrupted POSIX/Winsock writes that report no bytes,
bounds syscall chunks/results to `INT_MAX`, and latches zero-progress/fatal
errors across flush, direct and buffered paths. It retains the current blocking
descriptor policy; `EAGAIN`/`EWOULDBLOCK` are terminal rather than a new
nonblocking readiness mechanism.

The TLS driver clears OpenSSL's error queue before writing and classifies
failures in the same thread under its connection mutex. It latches the first
failure, converts every unsuccessful OpenSSL write result into a generic
write failure, preserves useful close/syscall/I/O status, and prevents later
TLS read/write/pending/shutdown calls on the failed connection. Descriptor I/O
shutdown wakes a blocked peek reader; a final locked read check covers failure
between readiness and `SSL_read()`. Allocation failures release new SSL state.

This is the existing blocking TLS path. `SSL_ERROR_WANT_READ` and
`SSL_ERROR_WANT_WRITE` fail closed with an explicit unsupported-retry error.
Safe TLS retry would need identical buffer/length, readiness/deadline and
cancellation policies; those are not added here. TLS syscall failures, including
OpenSSL-classified interrupted syscalls, are terminal rather than blindly
replayed. These changes improve failure-path correctness; they are not a
normal-throughput claim or a diagnosis of earlier live disconnects.

See [PNG preparation](../docs/png-palette-preparation.md),
[browser readiness and benchmark limits](../docs/browser-render-scheduling.md),
and [socket failure semantics](../docs/socket-write-failures.md).

## Validation

The exact final native source passes **248 tests with diagnostics off**, **248
with diagnostics enabled**, and **248 in an actual compiler-TLS-disabled build**.
That is six additional PNG tests and seventeen socket tests over private.9.
The web build passes **56 Java, 177 Firefox common-JS and 33 frontend tests**;
the same client tree also passes all 177 common-JS tests in local Chrome.

exactly the final implementation's `28f85e39567776351ba94a09bb91ef4fd171f658`.
The matched final source label reuses that tested client build cache.

Fourteen PNG functions pass 25 local strict/UBSan repetitions (350 executions)
with real Cairo/libpng and an independent linear first-seen palette oracle.
Full PNG payload bytes and decoded pixels match across packing boundaries,
grayscale, old/new hash collisions, signed padded strides, bottom-reaching
views, prefix seams, exact/over-cap and tall-narrow staging, high-color/ARGB
fallback, optional/final OOM and libpng creation/output errors. Socket local
strict/UBSan checks pass nineteen selected cases with SSL/poll and twelve
without SSL/select. These cover partial writes, EINTR, zero/invalid counts,
Base64 vectors/boundaries, positive-error propagation, sticky failures,
TLS classification/ownership and pending/read/write/cleanup race boundaries.
Fault scripts bound retries, making historical spins deterministic failures.
They do not replace live TLS renegotiation or Windows runtime testing.

The six new browser regressions cover large sequential/shuffled frames,
earlier blockers holding back later frames, pre-flush unblocks, decode errors,
duplicate/stale callbacks, cancellation after a ready prefix and cancellation
during atomic drawing. Existing scheduling/decoder suites remain passing.
Independent reviews found no material blocker in all three components and
the configuration-preserving deployment helpers.

## Browser readiness measurements

The final six-sample and longer twelve-sample comparisons both alternate
version order, bind exact source/module hashes and use unmodified timing pages.

40 or 128 images and a target minimum source interval of 16 ms. Decoding, task

draw-order trace is not collected. Controlled fixtures and unit tests directly
verify task order. Summaries are medians of per-replay quantiles, not pooled
