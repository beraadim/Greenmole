# 1.6.1-private.7

Deployed to Oberon on 15 October 2026 at **22:51:04 CEST**
(`2026-10-15T20:51:04Z`), preserving the existing configuration.
This private build retains the Apache Guacamole staging/1.6.1 baseline,
private.6 resizing, browser receive budget and twelve-worker partial-batch policy.

## Changes

- Browser keepalive, ping, receive and unstable timers retain one pending timeout
  when their deadlines stay the same or move later. Earlier deadlines rearm
  immediately; cancellation rejects callbacks already queued by the browser.
  Monotonic intervals preserve the existing five-second/500-millisecond,
  activity-triggered one-shot behavior and wall-clock ping payloads. Client
  callback guards prevent obsolete connection work from affecting a replacement.
- Native copy searches skip empty indexes and stop at the next row boundary
  after candidates are exhausted. Scan order, full pixel comparison, collision
  handling and image fallback remain intact. A fixed 64×64 indexing hash uses
  two scalar accumulators instead of clearing a roughly 128 KiB rolling array
  for every cell. The search walker uses a direct typed lookup.
- Each display reuses bounded planner storage and clears only touched index
  buckets. Retained operation capacity stops at 4096 entries; oversized/nested
  plans are transient. Scratch is freed at display destruction after producers
  finish. Allocation failures abort before committing incomplete output, and
  stopped FIFOs reject late plan creation.

No connection settings, codec/quality policy, worker configuration, frame pacing
or Mac package changed. Existing macrdp 0.1.12 remains compatible.
See [timer deadlines](../docs/browser-timer-deadlines.md),
[planner storage/search](../docs/display-planner.md), and the
[production benchmark method](../docs/display-production-benchmark.md).

## Validation and performance

The final native image passes **192 tests**, including 13 planner regressions.
The matched web build passes **56 Java, 171 Firefox common-js and 33 frontend
checks**. All 171 common-js tests also pass in local Chrome. Twelve focused
native tests passed 25 local UndefinedBehaviorSanitizer repetitions. Hash tests
cover independent polynomial equivalence, high pixel bits, padding, nonzero
origins and copies between unequal strides. Timer tests cover cadence, activity,
throttling, wall-clock jumps, reentrancy, cancellation, EOF and replacement.

The web component is unchanged from the first tested private.7 build; subsequent
source commits affect native planning and benchmarks. Its final image reuses
that tested build cache and carries the final source label. Both browser records'
module bundle hash matches the modules committed in the final implementation:
`4c294902b9503d687744844d6030cb4a6365432dc4f0697b8ad776a77329f0c1`.

Uninstrumented Chrome replay versus exact private.6 improves large burst
completion approximately **9–14%**, with other-browser-task delays remaining
around 9–10 ms. Separate timer instrumentation counts 30,003–44,003 timeout
creations/cancellations per burst in private.6 and zero new ones in the candidate,
with four timer roles already pending. This does not mean idle connections use
no timers. Instrumentation adds overhead and is excluded from the completion
comparison. Raw samples and limits are retained in the
[browser protocol](1.6.1-private.7-browser-protocol-benchmark.json) and
[timer-count](1.6.1-private.7-browser-timers-benchmark.json) records.

Scrolling/redraw/mixed 4K p95 improves about **9%, 9% and 4%**, respectively.
Their mean indexing/search phase times improve approximately 12–15%. Solid and
early-copy cases benefit substantially from skipped work. Candidate counters
show 840 measured cache reuses and no plan/operation allocations or growth;
retained scratch stays flat at 1.13–1.28 MiB in these fixtures. The
4096-entry cap is approximately 1.44 MiB on Oberon. Baseline counters are absent,
so these measurements do not invent a baseline allocation count or establish
an overall process-memory reduction.

**Remaining photo tail:** `small-photo-on-4k` mean reported p95 increases 9.86%.
The forward order is nearly flat, while the reverse order increases 18.78%;
its median improves 4.30%, CPU increases 0.41%, and search-phase time falls.
This remains an unresolved order-sensitive tail, neither a proven planner
regression nor proven harmless noise. Most other photo/window p95 differences
are small; live photo-heavy responsiveness still needs user acceptance.

**Encoding caveat:** the full-wallpaper forward run changes protocol bytes from
about 18.5 MB to 3.7 MB per frame while image area and admission stay the same;
the reverse run does not show that large gain. The existing framerate-dependent
PNG/WebP/JPEG policy is unchanged, but can choose different output as the unpaced
fixture runs faster. Its total-cost result is not an isolated planner gain or
controlled equal-quality comparison and is excluded from headline claims.
The separate lossless correctness replay remains exact.

The forward run checks four lossless frames per case: **112 frames and
721,534,976 RGB pixel comparisons** across both versions, with matching expected
canvases and final hashes. The reverse run explicitly disables replay to focus
on timing. Checks decode real PNG/lossless WebP output and apply serialized
copies/fills; they include untouched visible pixels and validate stream/sync
completion. The verifier covers opaque fixed-size fixtures, not general alpha,
resize or browser behavior.

The [final native benchmark record](1.6.1-private.7-display-production-benchmark.json)
contains every case, both orders, phase measurements, counters, image IDs,
source labels and harness hash. Earlier candidates were rejected during
pre-deployment regression checks; exploratory records remain outside Git.
These are synthetic planner/FIFO/encoding/serialization measurements. They do
not establish capture, RDP transport, browser paint/FPS, physical-input or Wi-Fi
latency. No live desktop session was opened for deployment verification.
