## Changes

### Exact copy-search optimization

Separate the first 63 warm-up rows and each row's 63-pixel prefix from the
complete-window lookup loop. Only complete horizontal windows need vertical
accumulators; initialize that width rather than the full maximum-width array.
Hash 63/64-pixel rows with four independent base-62⁴ chains and combine them
using exact unsigned modulo-2⁶⁴ arithmetic. This shortens the dependency chain
for cell indexing and per-row prefixes without sampling or changing hash values.

Preserve row-major first-match order, candidate consumption, bitmap membership,
full pixel collision checks, copy choices and window counters. Do not advance
row pointers past the final row of bottom-reaching image views. Codec selection,
quality, compression, image geometry, frame boundaries and worker admission are
unchanged. Six new regressions cover 414 independently weighted row hashes,
441 small-window positions, maximum width, padded nonzero-origin bottom views,
incomplete regions, duplicate ordering and real rolling-hash collisions.

### Optional pipeline diagnostics

Native users reuse `GUAC_DISPLAY_DIAGNOSTICS=1` for numeric sync ACK age,
existing lag estimates and unacknowledged server-timeline span. Java's standard
WebSocket bridge has a separate trusted process opt-in for native-read idle/wait,
batch hold, send-lock/send and writer-lock/write durations. Browser Client APIs
provide local sync-to-ACK-attempt and sampled display-backlog snapshots.

All three remain off by default. Aggregates are bounded and saturating; no new
wire instructions, payload logging, capture or per-frame history are added.
Native and Java summaries are activity-driven, at most once per ten seconds per
user/endpoint. Each component uses its own clock; the measurements cannot be
subtracted across hosts or correlated frame by frame. READ includes ordinary
idle time, ACK attempts do not prove delivery, and queue sampling can miss spikes.
See [operator usage and limitations](../docs/display-timing-diagnostics.md).

Reject malformed, missing, negative and overflowing sync timestamps safely.
Saturate very old elapsed times instead of narrowing or overflowing integer lag
fields, while preserving fresh/duplicate/stale callback behavior. Append the
optional user field to preserve existing field offsets. Cancel browser samples
on disconnect/reconnect/state import; stale callbacks cannot update new totals.
A failing diagnostic Java logger disables only its collector and cannot strand
a writer lock or mask a forwarding failure.

### Direct-buffer candidate rejected

Implement and test direct Base64 decoding into an outstanding BYOB view, then
restore production `InputStream.js` and its tests byte-for-byte to private.11.
The safe canonical-input check is extra work: the final native Chrome BYOB study
was **2.80×, 5.69× and 6.41× slower** for 6,144-byte, 65,535-byte and 1 MiB blobs.
Separate counters confirm the candidate eliminated a buffer/copy, demonstrating
that fewer allocations alone do not establish a speedup. The actual Chrome
image decoder requested no BYOB buffers in the full replay, so this candidate
also offered no demonstrated benefit for that image path.

Keep the implementation in reachable commit `6046fa964`, a reproducible isolated
browser study and all negative results. Its new process helper bounds cleanup
when Chrome is already signaled, ignores graceful shutdown or fails to spawn.
Existing image decoding and compression defaults remain unchanged.
[Study](1.6.1-private.12-byob-study.json) ·
[Method and interpretation](../docs/byob-base64.md).

## Browser delivery

The default-off comparison uses identical production bytes with private.11 and
private.12 client bundles: **192 timing runs and twelve verification runs**,
2,304 measured frames, 152,776 ordered draw calls and 279,134,208 exact checked
canvas pixels. Every image ACK/draw/order check passes. All twelve verification
documents observe zero native ImageDecoder BYOB requests and zero payload copies
into BYOB buffers. Structural counters run only in untimed verification; timed
records contain no Base64 counters or enabled Client diagnostics.

Browser p95 changes across 24 scenario/profile pairs range from -7.94% to +4.85%,
or -2.275 to +1.175 ms. This is not a browser-speedup claim. The range is not
uniformly inside the earlier A/A control; PNG128/constrained is consistently
about 0.6 ms higher in the browser interval while its source-schedule proxy
changes only about 0.16 ms. Preserve that observation and the isolated tails.

An additional same-client diagnostic-on correctness probe passes 24 timing and
twelve verification runs, 8,112 ordered draws and 62,029,824 exact canvas pixels.
All 180 sync receipts/completions/ACK attempts match, including bootstrap syncs;
no samples remain in flight. This is an on/on correctness probe, not an on/off
instrumentation-overhead comparison.

The replay shapes downstream bytes and jitter but leaves ACKs on loopback; it
does not emulate Wi-Fi loss, TCP congestion or RTT. Low display queue depth can
coexist with unsent source-schedule debt (3.833 seconds in this replay). Intervals
overlap and cannot be added as independent stages; short per-run p95 values are
sensitive to outliers. Full original raw JSON is retained in deterministic gzip
files with compressed and original hashes/sizes.
