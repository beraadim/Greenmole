Deployed to Oberon on 15 October 2026 at 19:22:02 CEST
(`2026-10-15T17:22:02Z`), preserving the existing configuration. This internal

## Scope

- Stabilize remote resize requests while keeping local scaling and input
  immediate.
- Bound browser processing across incoming WebSocket protocol bursts while
  preserving instruction order and complete drawing operations.
- Apply workload-aware active encoder concurrency while retaining the existing
  persistent worker pool and administrative configuration. The selected
  partial-batch ceiling is twelve; final committed-source comparisons are
  recorded below.

## Resize stabilization

Viewport changes settle for 150 ms before requesting a remote resolution.
Continuous changes have a 500 ms maximum settling delay; only the latest desired
size is retained. Duplicate events do not postpone the deadline or repeatedly
send the same outstanding layout. Local auto-fit scaling and pointer-coordinate
mapping continue to use the actual display immediately, without waiting for the
remote resize.

Runtime dimensions are floored like the initial handshake, with even-width
normalization for RDP once its protocol is known. Other protocols retain odd
widths. A monitor/device-pixel-ratio change is detected even when CSS dimensions
stay the same. The first known viewport starts one connection attempt, and a
newer viewport received during connection is applied once size instructions can
be sent. Replacing or destroying the view cancels its pending requests and
listeners.

A matching remote size acknowledges the pending request. If an acknowledgment
does not arrive, the same layout is retried after 1.5 seconds, up to three sends.
Retries then stop in the background; a later viewport notification can re-arm an
expired request, and a different desired size always supersedes it. This avoids
both permanent duplicate suppression and endless reactivation of servers which
ignore or constrain resizing. Guacd's existing 500 ms native resize throttle is
unchanged. Connection settings and image-quality defaults are unchanged.

## Browser receive processing

The WebSocket receive path uses a connection-scoped instruction pump. Isolated
updates run synchronously; bursts yield through `MessageChannel` after eight
milliseconds or 4096 instructions, with a timer fallback. Large instructions
also check the cooperative budget every 32 elements. Callbacks receive only
complete instructions, and existing display-frame atomicity is preserved. A
single element or callback can exceed eight milliseconds; this is not a hard
execution deadline. HTTP streaming and ordinary `Parser.receive()` consumers
remain synchronous.

Receive buffering has a conservative 64 Mi-code-unit limit for source text,
retained elements and estimated metadata, a 4096-packet queue limit, and an
independent 16,384-element limit checked at parsing checkpoints. Empty arguments
count toward metadata and element limits. Overflow terminates the connection
with an explicit receive-buffer error instead of dropping dependent
instructions and continuing. These are application-buffer bounds, not exact
heap measurements or bounds on browser network buffers, decoded images or
display memory.

Network timers reset when packets arrive, before deferred parsing. Reentrant
receive calls remain ordered. Natural WebSocket EOF drains complete instructions
already received before terminal notification; manual disconnect or reconnect
cancels that drain immediately. Old socket, timer and continuation callbacks
cannot act on a replacement connection, and no messages are written after EOF.
Read-only review covered partial-instruction retention, empty-argument metadata,
overflow, cancellation, callback reentrancy, connection generations and final
instruction ordering at EOF. Focused regressions cover these cases.

See [bounded browser protocol processing](../docs/browser-protocol-budget.md)
for implementation limits and the repeatable comparison.

## Encoder admission

The persistent encoder pool and `GUAC_DISPLAY_WORKER_THREADS` remain unchanged.
For a frame whose final planned image area is below 4,194,304 pixels and below
half of the committed desktop area, the policy admits at most twelve image
encoders simultaneously. The selected limit also cannot exceed the real pool
or the number of image operations. Larger batches, full-window changes on
smaller desktops, and unknown desktop dimensions retain the available pool.
Copy/fill operations do not count as image area. These are limits on encoding
work, not capture rate, browser frame rate or image quality.

Admission occurs before removing an operation from the real FIFO or acquiring
a framebuffer lock. The limit is selected between frames under the FIFO lock
and remains fixed while that frame is processed. Completing workers wake
capacity waiters; FIFO invalidation wakes all waiters at shutdown. Non-image
frame completion retains an admissible worker, and partial pools use only
successfully created threads. Plan submission and policy configuration return
immediately after FIFO invalidation, preventing late producers from reading
pool counts during teardown or sending further plan instructions. Review
covered recursive lock depth during condition waits, admission accounting,
per-frame policy immutability and shutdown races.

Final verification compared the private.5 library with committed private.6
source through all nine production-path scenarios in both mode orders, then
ran a balanced text sequence: baseline, fixed, adaptive, fixed, baseline,
adaptive. Each run used 30 measured frames after five warm-up frames and the
same 22-worker pool. Fixed and adaptive use the same private.6 library; fixed
retains full-pool admission. The balanced results below are arithmetic means
of two per-run summaries, **not percentiles of pooled frame timings**:

| Synthetic workload | Private.5 mean reported p95 | Private.6 default mean reported p95 | Private.5 CPU/frame | Private.6 CPU/frame |
| --- | ---: | ---: | ---: | ---: |
| Text scrolling | 43.592 ms | 43.576 ms | 114.052 ms | 105.033 ms |
| Partial text redraw | 38.713 ms | 39.446 ms | 97.870 ms | 94.550 ms |

Against private.5, default admission used approximately 7.9% less process CPU
for scrolling and 3.4% less for partial redraw. Mean reported p95 was essentially
unchanged for scrolling and approximately 1.9% higher for redraw; mean reported
p50 was approximately 5% and 3% higher, respectively. This is a modest CPU
efficiency tradeoff, not evidence of faster window switching. The initial
target of a 15% scrolling-latency improvement was **not demonstrated**.

The first full sweep showed a 7–8% text p95 increase, while the reverse sweep
showed a 2–3% decrease. That mode-order variation prompted the balanced text
check. Across the two full sweeps, each large/full-window workload's mean
reported p95 was within 5% of baseline or lower. Many of those workloads retain
full concurrency, so favorable variation is not attributed to admission policy.

The photo-window checks also confirm that selection uses final planned image
area, rather than the incoming dirty rectangle. A 2560×1304 photo update within
a 4K desktop generated 15 image operations covering 5,632,000 pixels after
planning, exceeding the area guard and retaining all 15 useful workers. The
1920×944 case had only eight image operations, which limited concurrency to
eight independently of the twelve-worker ceiling.

[Encoder-worker documentation](../docs/encoder-workers.md) and the
[admission benchmark record](1.6.1-private.6-admission-benchmark.json) retain
the earlier candidate sweeps, ceiling tuning and photo checks. Those exploratory
runs used uncommitted exports whose OCI revision labels identify their parent;
they are separate from the final committed-source results above. The
[final production benchmark record](1.6.1-private.6-display-production-benchmark.json)
contains the forward, reverse and balanced-text results with source provenance
and benchmark image IDs. The baseline benchmark image lacks an OCI revision
label; its source is established from the preserved private.5 build context.
The harness includes planning, copy search, FIFO, encoding and serialization to
a discard socket; it does not include capture, RDP transport, browser painting,
Wi-Fi or physical input delay. The older isolated-codec measurements do not
establish production scheduling gains.

resize tests. Coverage includes fractional pixel density, fullscreen bursts,
the settling bound, duplicate requests, delayed/ignored/obsolete acknowledgments,
initial connection, protocol detection, monitor changes, immediate local scaling

The protocol replay compares the exact private.5 tag with the candidate through
the actual tunnel, parser, client and display code. It uses real canvas copies
and fills without injected drawing delays, checks every sync acknowledgment and
the final pixel, and measures when a separately posted browser task can run.
Four samples per version alternate execution order in foreground headless
Chrome 155 on macOS ARM64. Source hashes and individual samples are recorded in
[the browser protocol benchmark](1.6.1-private.6-browser-protocol-benchmark.json).

| Synthetic burst | Private.5 completion | Candidate completion | Private.5 other-task delay | Candidate other-task delay |

| 22,000 small copy frames | 77.45 ms | 90.35 ms | 78.30 ms | 9.15 ms |

These medians show less blocking of other browser tasks during large bursts,

These synthetic measurements and deployment checks do not establish real
desktop responsiveness. Live RDP and Wi-Fi acceptance remain separate.
